# Transaction-scoped logging across the RAG service

**Jira:** DD-43721 · **Status:** implemented (this document is the reference architecture for logging in this repo)

## Purpose

Every log line written during one invocation of any of the five function apps carries the ID of the **journey** it belongs to, so that a single Kusto search in Application Insights returns the complete, ordered story of one answer request or one document upload across every app it touched. Nothing in the service or shared-artefacts classes changes to achieve this: the ID is attached once at the function entry point and inherited by every line written on that thread.

This page is both the design record and the convention new code must follow. The short version:

- Open a `LogContext` in try-with-resources around the **whole body** of every `@FunctionName` method.
- `put` the journey key as soon as it is known (`TRANSACTION_ID` on the answer journey, `DOCUMENT_ID` on the document journey) and `CLIENT_ID` once the identity is resolved.
- Log through SLF4J as before. Never pass IDs through method signatures just to log them, and never use `context.getLogger()`.
- Keep the five `log4j2.xml` pattern lines identical (a shared-artefacts test enforces this).

## Problem

Before this change only 43 of the 168 log statements across the five apps mentioned the ID of the journey they belonged to, and nearly all of those sat in the function classes themselves. Every line written by a service or shared-artefacts class (search, chat, embedding, Document Intelligence, chunking, table, blob, idempotency) was anonymous: when two requests ran on the same app instance their lines interleaved with nothing to separate them.

The ID was missing from those lines because it never reached them. The services are constructed once per app instance and take no per-request context, so a developer could not add it to a message without changing method signatures.

| App | Log statements | Mentioned the journey ID |
|---|---|---|
| answer-retrieval | 99 | 23 |
| ingestion | 46 | 12 |
| scoring | 13 | 3 |
| metadata-check | 8 | 4 |
| status-check | 2 | 1 |
| **Total** | **168** | **43** |

## Current state (what the design builds on)

- Every class in all five apps logs through **SLF4J backed by log4j2** (`log4j-slf4j2-impl`), writing to stdout through a console appender. Nothing uses `context.getLogger()`.
- A line reaches Application Insights as a console trace: log4j2 → stdout → the Functions Java worker → the host → App Insights `traces`. No Application Insights Java agent is enabled in any environment.
- `host.json` sampling excludes only `Request`, so traces are sampled in every environment.
- **Every pipeline is single-threaded per invocation.** No executor, `CompletableFuture`, parallel stream or thread creation exists on any app's path or in shared artefacts, which is what makes a thread-local context safe. The metadata-check host runs up to 50 blob-trigger invocations concurrently (`maxDegreeOfParallelism`), but each runs on its own worker thread with its own context.

## Options considered

| Option | How it works | Footprint | Verdict |
|---|---|---|---|
| Thread the ID through method signatures | Add a `transactionId` / `documentId` parameter to every service and shared method on the path and print it in each message | Every one of the 168 statements plus most service and shared-artefacts signatures | Rejected: largest change, and does nothing for SDK-internal lines |
| Switch to `context.getLogger()` | Use the per-invocation `java.util.logging` logger the host supplies; the host stamps each line with the invocation ID | The logger object must be passed into every class, including shared artefacts used by five apps and the offline harness; JUL has no MDC; every statement rewritten | Rejected: the same plumbing problem with a worse logging API |
| **SLF4J MDC (mapped diagnostic context)** | Put the ID into the thread-local MDC once at the function entry point; the log4j2 pattern prints it on every line written on that thread | One shared helper, nine entry points, one pattern line in five files; zero existing statements touched | **Chosen** |

SLF4J's MDC maps onto log4j2's `ThreadContext` through the bundled `log4j-slf4j2-impl` adapter, so no new dependency was needed.

## Design

### Journeys

Two journeys run through the service, each with one ID that is known at every hop. The synchronous answer endpoint is the only path with no journey ID: it is correlated on its invocation ID, which it carries forward to its scoring run.

| Journey | Key | Functions, in order | Where the ID is known at each hop |
|---|---|---|---|
| Answer (async) | `transactionId` | `InitiateAnswerGeneration` → `AnswerGeneration` → `GetAnswerGeneration` → `AnswerScoring` | generated by `randomUUID()`; queue payload; path parameter; scoring blob payload |
| Answer (sync) | `invocationId`, then `originInvocationId` | `AnswerRetrieval` → `AnswerScoring` | host invocation ID; scoring blob payload (`ScoringPayload.originInvocationId`) |
| Document | `documentId` | `InitiateDocumentUpload` → `DocumentUploadCheck` → `DocumentIngestion` → `DocumentStatusByReference` | request body; blob name via `DocumentBlobNameResolver`; queue payload; path parameter `documentReference` |

### Correlation keys

| Key | Printed as | Source | Present on |
|---|---|---|---|
| `invocationId` | `inv=` | `ExecutionContext.getInvocationId()` | All nine functions, from the first line of the invocation |
| `transactionId` | `txn=` | Queue payload (worker), generated UUID (initiate), path parameter (status), scoring blob (scoring) | Answer journey only; never on the synchronous endpoint, which has no transaction |
| `documentId` | `doc=` | Request body after validation (upload), blob name via the resolver (upload check), queue payload (ingestion), path parameter (document status) | Document journey only |
| `originInvocationId` | `origin=` | `ScoringPayload.originInvocationId`, set by the synchronous endpoint to its own invocation ID | Scoring, only when scoring a synchronous answer |
| `clientId` | `client=` | `ClientContext` after the identity resolver (HTTP functions); the payload (workers) | Every function when `CLIENT_FILTERING_ENABLED` is on; absent otherwise |

Keys are **typed** (`txn=` / `doc=`) rather than one generic `correlationId`: each app only ever has one journey, but a typed key makes a Kusto query unambiguous and costs nothing when absent. A line never carries both.

`invocationId` is what ties the synchronous endpoint's lines together, and it also lets any line be joined to the host's own request telemetry for that invocation.

### The helper: `uk.gov.moj.cp.ai.logging.LogContext` (shared artefacts)

Deliberately tiny: `open(ExecutionContext)` seeds `invocationId` and **clears first** (worker threads are reused, so a leaked key would attach one request's ID to the next request's lines); static `put(key, value)` for keys learned part-way through the invocation (null values are ignored, so optional payload fields need no guard); `get(key)` for the rare case where code needs the current value; `close()` always clears. Always used in try-with-resources so the close happens on every exit path, including a worker's deliberate rethrow for queue redelivery.

```java
public final class LogContext implements AutoCloseable {
    public static final String INVOCATION_ID = "invocationId";
    public static final String TRANSACTION_ID = "transactionId";           // answer journey
    public static final String DOCUMENT_ID = "documentId";                 // document journey
    public static final String ORIGIN_INVOCATION_ID = "originInvocationId"; // scoring of a sync answer
    public static final String CLIENT_ID = "clientId";

    public static LogContext open(final ExecutionContext context) { ... } // MDC.clear(), then seed invocationId
    public static void put(final String key, final String value) { ... }  // null-safe MDC.put
    public static String get(final String key) { ... }
    @Override public void close() { MDC.clear(); }
}
```

### Entry-point wiring

The pattern is the same in all nine functions: the public `run` method opens the scope and delegates to the existing body, renamed to a private method (`handle` for HTTP functions, `process` for triggers). Tests keep calling `run`, so no test changes were forced beyond the two functions that gained an `ExecutionContext` parameter (`DocumentUploadCheck`, `DocumentIngestion`; the host injects it on any trigger type).

```java
@FunctionName("AnswerGeneration")
public void run(@QueueTrigger(...) final String queueMessage,
                @QueueOutput(...) final OutputBinding<String> scoringMessage,
                @BindingName("DequeueCount") long dequeueCount,
                final ExecutionContext context) {
    try (LogContext ignored = LogContext.open(context)) {
        process(queueMessage, scoringMessage, dequeueCount);
    }
}

// inside process(), once the payload is validated:
LogContext.put(LogContext.TRANSACTION_ID, transactionId.toString());
LogContext.put(LogContext.CLIENT_ID, claimClientId);
```

Where each key is learned:

| Function | `transactionId` / `documentId` | `clientId` |
|---|---|---|
| `InitiateAnswerGeneration` | immediately after `randomUUID()` | after the identity resolver |
| `AnswerGeneration` (worker) | after the queue payload is validated | from the payload, after `ClientId.requireValidOrNull` |
| `GetAnswerGeneration` | the raw path binding, before the body runs (validated inside) | after the identity resolver |
| `AnswerRetrieval` (sync) | none — `inv=` is the key; the invocation ID is written into `ScoringPayload.originInvocationId` | after the identity resolver |
| `AnswerScoring` | `txn=` **or** `origin=` from the blob, once it is read | from the blob |
| `InitiateDocumentUpload` | the body's `documentId`, once validation has passed | after the identity resolver |
| `DocumentUploadCheck` (blob trigger) | from the blob name via the resolver | from the blob name via the resolver |
| `DocumentIngestion` (worker) | from the queue payload | from the payload, after `ClientId.requireValidOrNull` |
| `DocumentStatusByReference` | the raw `documentReference` path binding (validated inside) | after the identity resolver |

Everything downstream — `IdempotencyGuard.runOnce` (which runs the work on the calling thread), the table/blob services, the chat and embedding services, the client factories — logs on the invocation thread and picks the keys up automatically.

### Linking a synchronous answer to its scoring run

The sync endpoint saves the scoring blob under a random UUID and enqueues only that filename; the payload's `transactionId` is null. Without a link, the scoring run for a sync answer could only be matched to its request by query text and timestamps. `ScoringPayload` therefore gained an additive, nullable, kept-last field `originInvocationId` (the same convention as `clientId`): the sync endpoint sets it to its own invocation ID, the async worker leaves it null, and the scorer puts it on the thread as `origin=`.

The record also gained `@JsonIgnoreProperties(ignoreUnknown = true)` because the shared `ObjectMapper` is strict about unknown properties — see *Rollout* for the one-release compatibility consequence.

### Attempt number on the queue workers

Each of the three queue workers logs one line per invocation, `Event attempt count N of M` (`N` = the host's `DequeueCount` binding, `M` = `maxDequeueCount` from `host.json`). Redeliveries are fresh invocations with their own `inv=`, so the attempt line joins to every other line of that attempt through `inv=`, and a search for `attempt count 3 of 3` answers "how often do we hit the final attempt". The attempt is deliberately **not** an MDC key: the invocation ID already separates attempts, and keeping the pattern to five keys was preferred over stamping every line.

### Pattern layout

One line, identical in each of the five apps' `src/main/resources/log4j2.xml`. `%notEmpty{}` suppresses the bracket when a key is absent, so lines outside an invocation (startup, client factories) stay clean and a line only ever shows the keys its journey has.

```xml
<PatternLayout pattern="%d{HH:mm:ss.SSS} [%t] %-5level %logger{36}%notEmpty{ [txn=%X{transactionId}]}%notEmpty{ [doc=%X{documentId}]}%notEmpty{ [origin=%X{originInvocationId}]}%notEmpty{ [inv=%X{invocationId}]}%notEmpty{ [client=%X{clientId}]} - %msg%n"/>
```

An answer-worker line written by a service class that knows nothing about the context:

```text
12:01:15.188 [pool-2-thread-1] WARN  u.g.m.c.r.service.ResponseGenerationService [txn=3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90] [inv=0d1c7a4e-8b2f-4c6d-9e1a-3b5c7d9f1a2b] - Citation guard (off): delivering citation-degraded answer without retry — [guard=off] Citations missing: jsonBlock=false, inlineMarkers=3, rendered=0, stripped=3.
```

and an ingestion line:

```text
12:04:02.311 [pool-2-thread-3] INFO  u.g.m.c.i.service.DocumentChunkingService [doc=7c1e2b9a-4d3f-4a8e-b6c5-0f1e2d3c4b5a] [inv=5e6f7a8b-9c0d-4e1f-a2b3-c4d5e6f7a8b9] - Document chunking completed: 42 chunks created
```

### Querying in Application Insights

With no further infrastructure change, correlation is a text search on the message:

```kusto
// one async answer, end to end (retrieval app + scoring app)
traces
| where message contains "txn=3f2a9c1e-5b7d-4e8a-9c21-7d4e5f6a8b90"
| project timestamp, cloud_RoleName, message
| order by timestamp asc

// one document, end to end (metadata-check + ingestion + status-check apps)
traces
| where message contains "doc=7c1e2b9a-4d3f-4a8e-b6c5-0f1e2d3c4b5a"
| project timestamp, cloud_RoleName, message
| order by timestamp asc

// a synchronous answer: its own lines, then its scoring run
traces
| where message contains "inv=0d1c7a4e-8b2f-4c6d-9e1a-3b5c7d9f1a2b"
   or message contains "origin=0d1c7a4e-8b2f-4c6d-9e1a-3b5c7d9f1a2b"
| order by timestamp asc

// how often a worker reaches its final delivery attempt
traces
| where message contains "Event attempt count 3 of 3"
| summarize count() by cloud_RoleName, bin(timestamp, 1d)
```

### What deliberately stays as it is

- **Messages no longer repeat the journey ID.** A second sweep removed the transaction / document ID from the 31 function-app statements that printed it (the key now arrives from the pattern, so a line read `… [txn=…] - Answer generation completed in 1840 ms`). Four kept an ID on purpose: `GetAnswerGeneration`'s "transactionId is required" (the word, not a value), `CitationProcessor`'s merge line (the *cited* document, not the journey's), and nothing else in the apps. The nine shared-artefacts table-service lines keep theirs: library code cannot assume its caller opened a scope (the eval harness and migration tool call them without one). Exception messages (for example the redelivery message asserted by tests) are not log statements and are unchanged. No alert or dashboard in `cpp-terraform-functionapp-deployment` searched for the old `transactionId=` / `documentId=` text (checked 2026-10-01).
- Service and shared-artefacts classes are otherwise untouched.
- No environment variable, `host.json` or API contract change. The only payload change is the additive `originInvocationId` field on the internal scoring blob.
- The migration tool and the evaluation harness keep their original pattern: neither runs under the Functions host, so they have no invocation to scope.

## Testing

Three layers, all unit-level; no integration-test change.

1. **`LogContextTest`** (shared artefacts): `open` clears stale keys and seeds `invocationId`; `put` with a null value is a no-op; `close` clears every key; a null context opens an empty scope; and SLF4J MDC keys are visible to log4j2's `ThreadContext`.
2. **`Log4j2PatternTest`** (shared artefacts): reads the five apps' real `log4j2.xml` files, asserts they declare **one identical pattern**, and renders a log event through that pattern inside an open scope, proving the end-to-end claim ("a service line carries the ID without the service knowing about it") and that a line outside any scope has no empty brackets.
3. **One `*LogContextTest` per function** (nine classes): the journey key is on the thread when the first service/table call happens (captured inside a Mockito answer), and MDC is empty after `run` returns — on success and on the exceptional exit (redelivery rethrow, scoring failure, blob-trigger failure). The scoring test covers both blob shapes (`txn=` for async, `origin=` for sync); the sync test asserts the saved `ScoringPayload` carries `originInvocationId`. `ScoringPayloadTest` covers legacy blobs without the field and blobs with unknown future fields.

## Risks and limits

- **Thread-locality.** MDC lives on the invocation thread. Every app's pipeline is single-threaded today (verified). If a future change introduces an executor, parallel stream or `CompletableFuture`, the keys must be copied across with `MDC.getCopyOfContextMap()` / `MDC.setContextMap(...)` in the submitted task. The same note is in `CLAUDE.md`.
- **SDK-internal threads.** Azure SDK and OkHttp lines emitted from their own I/O threads (Netty reactor, OkHttp dispatcher) do not carry the keys. Application code calls the blocking clients, so every line the team writes is on the invocation thread. Acceptable.
- **Leaked keys on reused threads.** Mitigated by `open` clearing on entry and `close` clearing on exit, with try-with-resources guaranteeing the close on every exit path.
- **Text-embedded, not structured.** Until the App Insights Java agent is enabled, correlation in Kusto is a `contains` on the message — adequate for tracing one journey, not for joins or aggregation by journey. See follow-ups.
- **Sampling.** `host.json` samples traces in every environment (`excludedTypes: Request` only). A sampled-out line is missing regardless of correlation; if complete per-journey traces matter, add `Trace` to `excludedTypes` for the app concerned, at the cost of ingestion volume.
- **The synchronous endpoint has no caller-visible ID.** Its lines correlate on `invocationId`, and its scoring run is linked through `originInvocationId`, but the caller never sees either. Returning a correlation ID to the caller would be a contract change in `api-cp-ai-rag` (follow-up).
- **Scoring blob compatibility (one release).** The shared `ObjectMapper` fails on unknown properties and `ScoringPayload` had no `@JsonIgnoreProperties`, so a scorer on the previous release cannot read a blob written by a retrieval app on this one. The annotation is now in place so the *next* additive change is safe; for this one, promote the scoring app before (or together with) the answer-retrieval app. Legacy blobs without the field deserialise with it null.

## Rollout

A normal release: merge to `main` cuts the release, bump each of the five apps' `version` in the environment tfvars (`cpp-functionapp-deployment`), run the deployment pipeline. **Promote the scoring app before, or together with, the answer-retrieval app** (see the compatibility risk: a synchronous answer scored in the window between a new retrieval app and an old scorer fails deserialisation and poisons after two attempts; that groundedness score is lost, nothing else is affected).

Verify in App Insights on dev with one async request and one document upload: every trace for the answer journey should carry the same `[txn=...]` across the retrieval and scoring apps, and every trace for the document journey the same `[doc=...]` across the metadata-check, ingestion and status-check apps.

## Follow-ups (separate tickets)

1. **Structured correlation via the Application Insights Java agent.** An app-setting change in `cpp-functionapp-deployment` per function app, no code change: `APPLICATIONINSIGHTS_ENABLE_AGENT = "true"`. The agent captures log4j2 directly, correlates each line with the invocation's `operation_Id`, and exports MDC entries as `customDimensions` (on by default in agent 3.x), so Kusto becomes `traces | where customDimensions.transactionId == "..."`. Trial it on dev first: the agent changes what the host emits for console output (lines may appear twice until console capture is turned off) and adds a small cold-start cost.
2. **Caller-visible correlation ID for the synchronous endpoint.** Return the invocation ID to the caller, for example as a response header, so a reported bad answer can be quoted by ID the way an async transaction can. Contract change in `api-cp-ai-rag`; this change already carries the ID to scoring, so only the HTTP surface is new.

## Convention for new code

- A new `@FunctionName` method: open `LogContext` in try-with-resources around the whole body; `put` the journey key as soon as it is known; nothing else.
- A new queue worker: also log `Event attempt count {} of {}` once at entry from the `DequeueCount` binding.
- A new additive field on a queue/blob payload: nullable, kept last, backward-compatible constructor, and the record carries `@JsonIgnoreProperties(ignoreUnknown = true)` (the shared `ObjectMapper` is strict). Mind the deploy-order consequence for the *first* field added to a record that lacked the annotation.
- A new function app: copy the `log4j2.xml` pattern verbatim and add the module to `Log4j2PatternTest.functionAppLog4j2Files()`.
- Never add a journey ID to a service method signature just to log it, and never use `context.getLogger()`.
